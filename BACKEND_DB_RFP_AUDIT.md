## 2. Findings, in severity order

### F02 — A published rule's new child rows remain mutable, and impact approval is not bound to the evaluated version

**[SEVERITY: blocker] [TYPE: present-but-wrong]**

**TENDER:** RUL-03, §3.1 p6: “A rule change must trigger impact analysis: affected registrations, teams, fees, quotas, documents, schedules and communications. No reclassification may occur silently.” RUL-04 preserves original/current category, reason, approving user and timestamp. RUL-05 requires rule **and sport-guide** versions to be publishable/exportable/auditable and affected participants notified. §7.7.4 p17 requires “named OC approval and a before/after audit record.”

**PLAN:** The update adds `rule_impact_analysis`, per-entry impacts and `rule_notification` ([P:406](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:406>), [P:420](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:420>), [P:430](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:430>)), including recipient acknowledgement. Its activation CHECK only tests a non-null analysis FK ([P:450](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:450>)). The header immutability trigger protects four fields ([P:311](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:311>)), while new dimension/predicate tables have no published-version mutation guard ([P:353](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:353>), [P:465](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:465>)). Default privileges grant app_rw UPDATE/DELETE on these child rows ([P:140](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:140>)). [P:30](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:30>) still pins entries “forever”; [P:554](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:554>) still has one rule FK, and `category_audit` [P:626](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:626>) retains only ages/category names for the decision.

**WHY IT FAILS:** Updating a dimension's bands or eligibility params changes the meaning of an already-referenced version without firing the header trigger. An analysis can also be attached to a different version: the FK proves the analysis exists, not that its `rule_version_id` matches the activating row. Even a correctly attached analysis becomes stale if child rules or participant facts change afterwards. A count/category-only result does not define fee/quota/document/team/comms impact, and no sport-guide artifact/version is linked. Header approval/publication metadata and effective upper bounds also remain mutable. A participant can therefore be evaluated under changed content carrying the same supposedly immutable version ID.

**EVIDENCE:** [P:313](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:313>)'s protected tuple excludes all child contents; [P:140](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:140>) grants their mutation; [P:451](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:451>) references analysis ID alone. This is a concrete bypass of the tender's no-silent-change guarantee, not a complaint about missing table names. [wms_domain/domain/models/teamRoster.ts:25](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_domain/domain/models/teamRoster.ts:25>) already includes rule identity/version in category audit records, while the proposed record drops them.

**REFUTATION / SCOPE:** Analysis and notification tables now **exist**, and are a useful correction. RUL-05 does **not** require acknowledgement; [P:400](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:400>) incorrectly calls it a Must. `summary` JSON can honestly hold a complete analysis if given a typed contract. Approved grandfathering is possible, but must be a recorded policy/decision, not an unconditional “original version forever” rule inconsistent with controlled revalidation. Scheduling impacts become active when Phase C supplies schedules.

**FIX:** Freeze dimension/predicate rows against insert/update/delete once their parent is published; make every change a new complete version. Bind analysis to that version and immutable input/configuration hashes or snapshots; verify freshness and named approval before activation/application. Define all tender impact dimensions in the analysis envelope. Preserve original and current evaluation records separately, including exact rule/fact/guide versions, reason and approver. Link notification content/delivery to the applied change. Restrict header mutation to an authorised audited range closure. Retain acknowledgement as product policy, not a tender gate.

### F03 — Quotas cannot represent independent shared allocations and release waves

**[SEVERITY: blocker] [TYPE: structurally-impossible]**

**TENDER:** REG-09, §4.2 p8: “Provide quotas, reserved allocations, release waves, local/international or other authorised quota dimensions”; §3.2 proficiency, p7 requires “grade-specific fees/quotas”; §2.2.4 p5 requires controls “at sport, discipline, event, category and venue level.”

**PLAN:** [P:666](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:666>) requires one product per quota and allows only `category_id` as a dimension; [P:677](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:677>) makes `(product, category)` unique, including NULL. [P:563](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:563>) permits one `quota_id` on an entry. `reserved` at [P:673](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:673>) is a held-count, not a reserved local/sponsor allocation policy.

**WHY IT FAILS:** An entry cannot carry consumption of both a sport-wide cap and a venue/category/local allocation. A product/category key offers no independent allocation population or shared-pool relationship. A release-wave date, eligible population and capacity tranche have no representation. The capacity CHECK can faithfully enforce the wrong aggregate; concurrency correctness does not establish tender coverage.

**EVIDENCE:** [wms_domain/domain/models/registrationJourney.ts:95](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_domain/domain/models/registrationJourney.ts:95>) has the same restricted dimensions; [wms_api/src/data/mockRegistrationJourneyRepository.ts:249](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_api/src/data/mockRegistrationJourneyRepository.ts:249>) selects by product/category only. Thus the current code supplies no hidden allocation policy.

**REFUTATION / SCOPE:** The new category tuple can include proficiency grade, so separate grade quotas are no longer inherently impossible. Encoding “local allocation wave 2” into that category would still conflate allocation policy with the award category and would not enforce shared parent caps. Deriving every shared cap in application code would require new policy configuration and consumption semantics; these are not in the plan. Registration quotas are Phase B, even when a venue catalogue later supports schedules.

**FIX:** Introduce scoped quota pools and allocation eligibility/release rules, plus `entry_quota_consumption(entry_id, quota_pool_id, units, state, expires_at)` allowing multiple applicable pools. Define whether units mean athletes, teams, entries or seats. Keep genuine category identity separate. Lock/check all consumed pools atomically using the prior concurrency design.

**CONFIDENCE:** **99%** — explicit uniqueness/cardinality restriction against explicit tender dimensions.

### F01 — The new dimension model lacks rule scope and sport-specific verified facts

**[SEVERITY: blocker] [TYPE: present-but-wrong]**

**TENDER:** RUL-01, §3.1 p6: “Rules must be configurable by sport, discipline, event, gender/category, team type, competition grade, venue, phase and effective date.” §3.2 p7 requires handicap “issuing authority, index/value, validity, verification and event-specific use” and judo multi-attribute eligibility/verification. §9.1.3 p18 requires ability to model §3 patterns and demonstrate representative scenarios.

**PLAN:** The updated plan now has `rule_dimension` ([P:353](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:353>)), `rule_eligibility` ([P:465](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:465>)), `entrant_attribute` ([P:488](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:488>)) and `category_combination` ([P:520](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:520>)). This closes the original “age only / no columns anywhere” complaint. But `rule_set` still scopes only event/sport/discipline/event-name ([P:278](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:278>)), and `entrant_attribute` is unique per `(event_id,person_id,attribute)` ([P:499](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:499>)), with one value, expiry, ordinary-document FK and recorded time. It has no sport/product/issuer scope, verified fact status or immutable fact-version contract.

**WHY IT FAILS:** One person can have licences from different sport federations, different event-specific proficiency reviews or different class determinations. The same unscoped attribute name cannot retain these independent facts and their decision basis. An entry's grade string partially handles grade selection, but does not resolve which verified fact a rule consumes. Document approval verifies a document; it does not record which extracted value/issuer was accepted for which product. New dimensions still cannot select independently scoped rule sets by gender/grade/venue/phase. The three mandatory rounding choices also need a defined precision-preserving path for handicap/weight; applying integer floor/round/ceil indiscriminately would alter those facts.

**EVIDENCE:** [wms_domain/domain/models/rule.ts:10](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_domain/domain/models/rule.ts:10>) and [wms_domain/features/rules/engine.ts:60](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_domain/features/rules/engine.ts:60>) still implement four age strategies, while [wms_domain/domain/models/registrationJourney.ts:31](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_domain/domain/models/registrationJourney.ts:31>) exposes the old product contract. The new design is a real domain change; [P:377](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:377>)'s mechanical migration claim and [P:1382](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:1382>)'s unchanged-interface promise do not establish support for the new evaluator. The tender's event-specific use and rule-scope clauses settle the required distinction.

**REFUTATION / SCOPE:** A validated JSONB rule definition is legitimate; SQL columns for every conceivable sport are unnecessary. New range/enum dimensions, predicate params, attribute values/expiry and a combination relation are useful additions, so do not call the six patterns wholly absent. Attribute names could be dynamically namespaced, but the dictionary, applicability, precedence and verification contract must then explicitly carry that scope. Generic audit can preserve fact versions if its envelope and lookup are defined. Competition combination execution remains Phase C.

**FIX:** Define rule selectors/precedence and a typed attribute dictionary with sport/product/issuer applicability; separate declared facts from verified decisions and record their source, validity and version. Link evaluations to immutable fact versions/snapshots. Specify operator semantics, precision/rounding and unsupported-input handling, then revise domain/repository/API contracts and prove all ten patterns from configuration. Use stable rule-scoped category/award identities for future combination/export.

**[SEVERITY: high] [TYPE: missing-additive]**

**TENDER:** PAY-03, §4.3 p9: “Support individual, captain/team, corporate/sponsor and OC-comped payment workflows, including split or staged payments if proposed.” TEA-02, §3.4 p7 requires “team deposits, payer sponsorship, split payments, unpaid roster members, deadlines”.

**PLAN:** The header entry FK is gone; `order_line.entry_id` now allows many entries per order ([P:709](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:709>), [P:737](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:737>)). [P:757](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:757>) says unpaid-member tracking is now simply entries whose line has no settled payment, but there is no payment-to-line relationship to query.

**WHY IT FAILS:** A ten-member order with a sponsor deposit and two participant contributions has a partially paid total. The records cannot distinguish “member A paid, member B unpaid” from the opposite allocation of that same total, nor attribute a partial refund to the debt it reopens. A line can name a deposit, but naming it does not allocate captured funds. The only payer remains the header's person, which also does not define the legal corporate billing party.

**EVIDENCE:** [P:757](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:757>)'s proposed query cannot follow a line-specific settlement link because [P:786](</Users/gauravgambhir/Desktop/Code_Life/wms/wms_participant/context_docs/docs/BACKEND_DB_PLAN.md:786>) stores only `order_id`. The tender mandates the behaviour, not one particular physical order design.

**REFUTATION / SCOPE:** Group orders, multiple intents/stages, team/corporate/comped kinds and deposit/balance line kinds are now supported. A documented proportional/FIFO allocation policy could be computed rather than fully materialised, but it must retain payer intent, reversals and the inputs needed to reproduce balances. No such rule is specified; treating every partially settled order line as equally paid/unpaid is inadequate for TEA-02.

**FIX:** Add contribution payer/billing-party identity, due obligations and payment/refund allocation to entry/member lines. Derive unpaid balances from settled allocations, including reversals, rather than from the order status alone. A grouped-order or deterministic allocated-ledger design is acceptable; preserve the newly correct many-entry line relationship.

The old CHECK could hold tax-inclusive prices, so the update's blanket historical claim that any VAT violated it is inaccurate.

**FIX:** Define fiscal source of truth and immutable seller/buyer/document/line/tax-group snapshots, locally or through an approved provider. OC finance must approve applicability, invoicing/receipt model and numbering rules before implementation.
